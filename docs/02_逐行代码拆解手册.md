# 2. 关键设计解释

## 2.1 scripts 为什么很薄

`scripts/*.py` 只解析命令行并调用函数。核心逻辑放 `src/fin_audio/`，因此 pytest 可以直接测试函数。

## 2.2 manifest 为什么分层

`qa_source.jsonl` 是文本源，`tts_plan.jsonl` 是确定性合成计划，`tts_status.jsonl` 是在线任务状态，`audio_qc.jsonl` 是音频技术结论，`provenance.jsonl` 是最终 lineage。

## 2.3 answer 为什么不会被修改

`source.py` 读取 `answer` 后直接保存为 `assistant_text`；normalizer 只接收 `source_user_text`；`dataset_builder.py` 直接使用 `src["assistant_text"]` 构造 assistant message。

## 2.4 mock 后端为什么存在

真实 Edge 是网络依赖。mock 优先调用本地 espeak 生成可听测试问题；没有 espeak 时才退回正弦信号。两种情况后续都走正式 MP3→FFmpeg→QC→JSONL。full 模式永远使用 Edge。

## 2.5 stable ID 的作用

同一 source row 永远对应同一个 SHA256，因此 split、voice、rate、WAV 路径都稳定，它也是 resume 主键。

## 2.6 原子写与 full 源冻结

JSON/JSONL/WAV/源 parquet 都尽量先写临时文件再原子替换；full 源 parquet 额外记录 SHA256。

## 2.7 长任务可观测性

TTS 每 100 条 checkpoint 并输出进度，Audio QC 每 1000 条输出一次 pass/fail/long，tmux 日志可直接观察。

## 2.8 long audio

超过时长上限的 WAV 移到 `long_audio/<shard>/`，并同步更新 tts_status，resume 不会再次生成。
